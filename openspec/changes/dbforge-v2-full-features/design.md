# Design: DBForge V2 全功能版本

## Context

DBForge 当前版本具备基础 CRUD 功能，但在实际使用中存在以下痛点：
1. 无法修改表结构（ALTER TABLE）
2. 无法管理索引、视图等对象
3. 多表操作需要频繁切换
4. 无法保存连接配置

## Goals

- 补全表管理全生命周期操作
- 支持多标签页并行工作
- 增强查询体验
- 提供连接配置管理

## Non-Goals

- 不实现完整的数据库设计器（ER 图作为简化版）
- 不实现完整的用户权限管理系统
- 不支持在线数据库（仅本地 SQLite + 远程 MySQL）

## Decisions

### 1. 表管理

**方案 A: 右键菜单** 
- 优点：操作直观，符合用户习惯
- 缺点：移动端支持较差

**方案 B: 工具栏按钮**
- 优点：易于发现
- 缺点：占用空间

**决策**：采用右键菜单 + 工具栏组合，核心操作右键提供，高频操作工具栏按钮。

### 2. 多标签页

**方案 A: React Router 多页面**
- 优点：URL 可分享
- 缺点：状态管理复杂

**方案 B: 状态驱动标签页**
- 优点：轻量，快速
- 缺点：刷新丢失

**决策**：采用 Zustand 状态驱动标签页，URL 仅用于默认状态。

### 3. SQL 自动补全

**方案 A: 自定义补全**
- 优点：完全可控
- 缺点：工作量大

**方案 B: CodeMirror SQL 插件**
- 优点：开箱即用
- 缺点：功能有限

**决策**：基于 CodeMirror @codemirror/lang-sql 的内置补全，增强表名/列名上下文感知。

### 4. 连接管理

**方案 A: 加密存储到 localStorage**
- 优点：简单，无需后端
- 缺点：浏览器清除丢失

**方案 B: IndexedDB 存储**
- 优点：持久化，支持大量数据
- 缺点：代码复杂度略高

**决策**：使用 localStorage 存储（加密处理密码），简单实用。

### 5. ER 图

**方案 A: 自研 Canvas 绘制**
- 优点：无依赖
- 缺点：工作量大

**方案 B: 使用 Mermaid.js**
- 优点：声明式，易用
- 缺点：需要依赖

**决策**：使用简化版表格卡片展示代替完整 ER 图，降低复杂度。

## Architecture Changes

```
src/
├── components/
│   ├── tabs/           # 新增：标签页管理
│   ├── table/          # 新增：表管理（右键菜单等）
│   ├── er-diagram/     # 新增：简化 ER 图
│   └── connection/     # 重构：连接管理
├── stores/
│   ├── tabStore.ts     # 新增：标签页状态
│   ├── connectionStore.ts  # 新增：连接配置
│   └── schemaStore.ts  # 扩展：表结构操作
└── lib/
    ├── sql-parser.ts   # 新增：SQL 解析（补全用）
    └── crypto.ts       # 新增：密码加密
```

## Trade-offs

- ER 图简化 vs 完整功能：选择简化版确保 MVP 可快速交付
- 右键菜单 vs 工具栏：组合方案平衡易用性和发现性
- localStorage vs IndexedDB：优先简单方案，后续可迁移

## Risks

1. **功能范围过大** → 拆分为多个小迭代
2. **CodeMirror 补全定制复杂** → 使用默认实现，后续优化
3. **状态管理复杂度** → 遵循单一职责原则
